# Threat model and limitations

The service handles potentially sensitive logs and event messages, and has a Kubernetes identity capable of reading pod metadata and logs within configured namespaces. Those data can contain credentials and instructions. Returned text must be treated as untrusted; the service cannot reliably redact secrets. Only grant namespaces and clients that may read all relevant logs.

Controls in the prototype include an explicit namespace allowlist, namespace-scoped read-only Roles, fixed log window and byte caps, request and response limits, timeout, bounded concurrent connections, Origin checking, and sanitized API error responses. Pod responses select status fields rather than returning full specs. The Kubernetes API client disables proxies and redirects, uses the cluster CA, and reads the projected token on each call. These controls have not been independently reviewed or exercised against a live Kubernetes API as this service.

The optional Cloudflare mode validates RS256 signatures, issuer, audience, expiration and an email allowlist at the origin, using a bounded cache of the configured issuer's keys. It does not query Cloudflare for per-token revocation; an otherwise valid assertion may remain usable until expiry. OAuth discovery, live Access behavior, JWKS rotation and policy revocation are unverified. The current shared bearer token lacks identity, scopes, expiry and automated revocation. HTTP has no transport encryption. NetworkPolicy is not supplied and ClusterIP does not prevent lateral access. Do not publish, deploy, or route this prototype. A future public endpoint requires authenticated TLS, independently reviewed origin assertions and a reviewed authorization policy. A compromised authorized client can read all allowed data; prompt injection, log disclosure, denial of service and stale or overbroad RBAC remain risks. The API itself must never be made public.
